# Notas del frontend sobre el contrato de API

Implementado tal cual `docs/API_CONTRACT.md`; no se usan endpoints que no aparezcan ahí. Puntos abiertos o supuestos que conviene confirmar con el backend:

1. **`text_es` de reglas editadas.** Cuando el usuario edita una regla (objeto, zona, orden o momento) o cambia el nombre de un objeto, el frontend regenera `text_es` en cliente (`src/lib/rules.ts`, frases con comillas para no equivocar el género) y marca la regla `origin: "user"`. Si el backend regenera el texto al hacer `PUT /rules`, prevalecerá el suyo en la siguiente carga.
2. **`present_in_zone` frente a `in_zone_at`.** El contrato no explica la diferencia. El UI ofrece los mismos campos (`object`, `zone`, `at`) para ambos. Las reglas nuevas que crea el usuario usan `present_in_zone`.
3. **Reglas nuevas.** Se crean con id `R{n}` libre, `origin: "user"` y `enabled: true`. Solo se pueden borrar las reglas propias que aún no estaban en el borrador del servidor. Las propuestas o hipótesis se desactivan, no se borran.
4. **Errores 422.** Se muestra `detail` tal cual en un aviso junto a las reglas. Si `detail` llega como lista (validación de FastAPI), se unen los `msg`. Antes de enviar, el cliente valida lo mínimo (al menos una regla activa, objetos con nombre y `sam_prompt`, `A ≠ B` y ausencia de ciclos de orden), pero el backend sigue decidiendo.
5. **Guardar y aprobar.** El botón principal hace `PUT /procedures/{pid}/rules` y después `POST /procedures/{pid}/approve`. Si el procedimiento ya está aprobado y no hay cambios, solo lleva a Verificar. Si el `PUT` funciona y el `approve` falla, se avisa de que los cambios quedaron guardados pero sin aprobar.
6. **Verificar sin versión aprobada.** La pantalla D se habilita cuando `status == "approved"` o `draft.approved`. Si existe una v1 aprobada y luego una v2 en borrador (`status` = `ready`), el UI pide aprobar antes de verificar. Si el backend permite verificar con la última versión aprobada, haría falta un campo tipo `approved_version` en la vista del procedimiento.
7. **`GET /runs/{rid}` y nombres.** El informe trae ids de objeto (`obj: "A"`). El frontend toma los nombres del borrador actual del procedimiento (`GET /procedures/{pid}`). Si ese borrador es de una versión posterior a la de la ejecución, los nombres podrían no coincidir. Sería útil que el informe incluyera las descripciones o que existiera `GET /procedures/{pid}?version=n`.
8. **`audit.status`.** Se trata como correcto si es `ok`, `success`, `succeeded`, `done` o `200`; cualquier otro valor se muestra como error junto con `error`.
9. **`camera_status` y `blocking_issues`.** Se traducen los códigos conocidos (`ALIGNED`, `MISALIGNED`, `MOVED`, `INSUFFICIENT_OBSERVATION`, `NO_OBSERVATION`, `CAMERA_MOVED`, `CAMERA_MISALIGNED`, `OCCLUSION`, `IDENTITY_AMBIGUOUS`). Los demás se muestran como código.
10. **Límites de archivo en cliente** (orientativos, en `src/components/DropZone.tsx`): MP4/MOV/WebM/M4V, ≤ 200 MB y entre 2 s y 120 s (aviso a partir de 60 s y en vídeos verticales). Conviene alinearlos con los límites reales del backend o de Meta cuando se midan.
11. **Sesión caducada.** Un 404 en `GET /sessions/{sid}/procedures` o al crear un procedimiento hace que el frontend olvide el `session_id` y vuelva a pedir consentimiento en la siguiente subida.
12. **Etiquetas de etapas.** Se usa `stages[].label` del backend. Mientras una etapa está en curso y no trae `detail`, se muestra un texto propio («Muse Spark está interpretando el video…», etc.) según `id` (`validate | interpret | segment | propose | verify`).
