# Frontend notes on the API contract

Implemented exactly as `docs/API_CONTRACT.md`; no endpoints that do not appear there are used. Open points or assumptions worth confirming with the backend:

1. **`text_es` of edited rules.** When the user edits a rule (object, zone, order or moment) or renames an object, the frontend regenerates `text_es` on the client (`src/lib/rules.ts`, phrases with quotation marks to avoid getting the grammatical gender wrong) and marks the rule `origin: "user"`. If the backend regenerates the text on `PUT /rules`, its own will prevail on the next load.
2. **`present_in_zone` versus `in_zone_at`.** The contract does not explain the difference. The UI offers the same fields (`object`, `zone`, `at`) for both. New rules created by the user use `present_in_zone`.
3. **New rules.** They are created with a free `R{n}` id, `origin: "user"` and `enabled: true`. Only the user's own rules that were not already in the server draft can be deleted. Proposals or hypotheses are disabled, not deleted.
4. **422 errors.** `detail` is shown as is in a notice next to the rules. If `detail` arrives as a list (FastAPI validation), the `msg` values are joined. Before sending, the client validates the minimum (at least one active rule, objects with a name and `sam_prompt`, `A ≠ B` and no order cycles), but the backend still decides.
5. **Save and approve.** The primary button does `PUT /procedures/{pid}/rules` and then `POST /procedures/{pid}/approve`. If the procedure is already approved and there are no changes, it just goes to Verify. If the `PUT` works and the `approve` fails, a notice says the changes were saved but not approved.
6. **Verify without an approved version.** Screen D is enabled when `status == "approved"` or `draft.approved`. If there is an approved v1 and then a draft v2 (`status` = `ready`), the UI asks to approve before verifying. If the backend allows verifying with the latest approved version, a field like `approved_version` would be needed in the procedure view.
7. **`GET /runs/{rid}` and names.** The report carries object ids (`obj: "A"`). The frontend takes the names from the procedure's current draft (`GET /procedures/{pid}`). If that draft is from a later version than the run's, the names may not match. It would help if the report included the descriptions or if `GET /procedures/{pid}?version=n` existed.
8. **`audit.status`.** It is treated as successful if it is `ok`, `success`, `succeeded`, `done` or `200`; any other value is shown as an error together with `error`.
9. **`camera_status` and `blocking_issues`.** The known codes (`ALIGNED`, `MISALIGNED`, `MOVED`, `INSUFFICIENT_OBSERVATION`, `NO_OBSERVATION`, `CAMERA_MOVED`, `CAMERA_MISALIGNED`, `OCCLUSION`, `IDENTITY_AMBIGUOUS`) are translated. The others are shown as a code.
10. **File limits on the client** (indicative, in `src/components/DropZone.tsx`): MP4/MOV/WebM/M4V, ≤ 200 MB and between 2 s and 120 s (a warning from 60 s and for vertical videos). They should be aligned with the real limits of the backend or Meta once measured.
11. **Expired session.** A 404 on `GET /sessions/{sid}/procedures` or when creating a procedure makes the frontend forget the `session_id` and ask for consent again on the next upload.
12. **Stage labels.** `stages[].label` from the backend is used. While a stage is in progress and carries no `detail`, its own text is shown («Muse Spark está interpretando el video…», etc.) according to `id` (`validate | interpret | segment | propose | verify`).
